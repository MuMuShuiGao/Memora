# ADR-0025：库快照走进程内 VACUUM INTO，盘外副本由本机计划任务拉取

> 状态：已废弃（被 0026 取代）
> 摘要：serve 每天导出一份 SQLite 快照并保留 5 份，Windows 计划任务每周 scp 拉到本机
> 日期：2026-11-27 ｜ 关联：[0007](0007-sqlite-over-postgres.md)、[design/memo-and-report.md §8](../design/memo-and-report.md)、`deploy/pull-backups.ps1`

## 决策

服务端 `serve` 启动时与之后每小时检查一次，距最新一份快照满 24 小时就用 `VACUUM INTO` 导出一份到 `MEMORA_BACKUP_DIR`，文件名带 UTC 时间戳，只保留最近 `MEMORA_BACKUP_KEEP` 份（默认 5）。盘外副本由 Windows 计划任务每周执行 `deploy/pull-backups.ps1`，scp 拉到本机，本机保留最近 5 份。

## 背景

[ADR-0007](0007-sqlite-over-postgres.md) 定了单文件 SQLite（WAL），备份就是复制库文件，但把"谁定期拷"留成了待确认。两点使"运行中直接复制"不成立：WAL 下最近的提交可能还在 `-wal` 里，单独拷 `.db` 会拿到不完整的库；云机只有一块盘，快照放同盘只防误删和写坏。数据量按日均几条估算，一年千条量级，快照的磁盘与时间成本都可忽略。

## 备选方案

| 方案 | 主要代价 | 结论 |
| --- | --- | --- |
| **进程内每日 VACUUM INTO 快照 + Windows 计划任务 scp 拉取** | 要部署新二进制并重启一次服务；快照与库同盘 | **采纳** |
| systemd timer + `memora backup` 子命令 | 多一个 unit、一次安装步骤和一套 CLI 参数 | 否决：换来的只是 serve 崩溃期间也能备份；serve 正常重启时"启动先补一次"已覆盖最常见的漏跑，不值得为这点覆盖再维护第二套调度 |
| 运行中直接 cp 库文件（连同 `-wal`/`-shm`） | 脚本几行就完，不碰 Go 代码 | 否决：三个文件不是原子拷贝，可能拿到撕裂快照；先 checkpoint 再拷要处理并发写，在 shell 里做对它的复杂度高于加一条 SQL |
| 服务端定时推对象存储 | 不依赖本机开机 | 否决：为一个单人库引入云凭据与外部可用性依赖，违背 ADR-0006 的最小运维面；本机计划任务已能拿到盘外副本，不需要服务端出网 |
| 只做同盘快照，手动拉取 | 实现最省 | 否决：这正是 NOW 挂着的那个问题——没有机制保证真做 |
| 定时停服后 cp | 逻辑最简单，一定一致 | 否决：每天为备份制造一次不可用窗口，备份不应有用户可感的代价 |

## 影响

- **得到**：每晚一份一致快照，误删或写坏可回到前一天；盘坏时最多丢一周（本机每周拉取）。
- **付出**：快照期间多一份磁盘占用（按库 10MB 以内估算）；上线需重启一次服务；盘外副本只在那台 PC 开着且连得上服务器时才生效。
- **返工点**：想改成持续复制或推远端，只动 `internal/backup` 与两个配置项，`store` 只多一个 `SnapshotTo`。
- **连带决定**：恢复步骤写进 design §8；`/etc/memora/memora.env`（口令哈希、模型 key）与 TLS 私钥不进自动快照（避免每天复制密钥），装机时各另存一份到本机——证书重签会让已装 APK 的证书固定失效，丢私钥要连带重发 APK。

## 复查条件

出现以下情况时重新评估本决策：

- 快照明显变慢（先按万条 / 10MB 量级估算，到跟前实测）
- 出现多实例或跨机器自动恢复的需求
- 云机换成自带快照能力的托管磁盘或数据库

## 替代成本参考

单机 SQLite 的同类做法是 `.backup` 命令或 Litestream 持续复制。Litestream 要常驻第二个进程并推对象存储，覆盖面更大，但超出这个项目"一个二进制 + 一个库文件"的边界。
