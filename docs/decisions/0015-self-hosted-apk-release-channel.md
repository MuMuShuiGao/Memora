# ADR-0015：更新包由自己的服务器分发，客户端检查后拉起系统安装页

> 状态：生效中
> 摘要：APK 更新走同一台服务器的同一端口与同一口令，服务端只读暴露版本元数据与安装包，客户端比版本号后提示并下载、由系统安装页收尾；所有变体统一用一把仓库外 keystore 签名
> 日期：2026-11-26 ｜ 关联：[0008-native-kotlin-client.md](0008-native-kotlin-client.md)、[0009-public-ip-selfsigned-https-access.md](0009-public-ip-selfsigned-https-access.md)、[0010-minimal-android-deps.md](0010-minimal-android-deps.md)、[../design/android-client.md](../design/android-client.md)

## 决策

更新通道复用已经在跑的那条 HTTPS：服务端加两个只读接口——`GET /v1/app/release` 回版本元数据（`version_code` / `version_name` / 大小），`GET /v1/app/release/file` 回 APK 本体，两者都挂在同一道口令校验后面。包放在服务器上一个固定目录里，发版动作就是把新 APK 和一份 `release.json` 拷进那个目录，服务端不写盘、不解包、不校验签名。客户端每次进主屏查一次，`version_code` 比内置的高就提示，用户点下载，进度走完交给系统安装页完成安装——最后那一下确认由 Android 自己给，不做任何绕过。

签名跟着一起定死：`debug`、`release`、`local`、`server` 四个变体统一用 `~/.android/memora.keystore`（别名 `memora`）签，keystore 与口令都留在仓库外，口令写在用户级 `~/.gradle/gradle.properties`。这样以后换构建类型不用卸载重装，覆盖更新的前提才成立。

## 背景

ADR-0008 只说了"产物是自己装的 APK"，ADR-0009 说了"换证书要重装 APK"，两条都没回答"改了代码以后怎么把新包送到手机上"。服务已经在公网跑起来（systemd + 8443 单端口），需求方要的是"像手机上的游戏一样能收到更新提醒"，而不是每次在电脑上找 APK 文件拷过去。已知约束：只有一个使用者、只开放一个端口（其余入站不放行）、公网 IP 与证书不进仓库（writing-rules §9）、客户端依赖按 ADR-0010 压到最小、这台 Windows 是唯一编译现场。

## 备选方案

| 方案 | 主要代价 | 结论 |
| --- | --- | --- |
| **自建 release 接口 + 客户端提示 + 系统安装页** | 服务端两条只读路由，客户端一段检查/下载/拉起安装的代码；每次发版多一步把包拷上服务器 | **采纳** |
| Google Play 内测轨道 | 25 美元开发者账号、Google 审核、要出 AAB、包交给第三方分发；需求方手机侧没有可用的 Play 客户端 | 否决：自动更新这条收益在最常用的场景里根本不成立，付出去的却是账号、审核和把包交给第三方三件事 |
| GitHub Release 放 APK | 仓库是公开的，而 APK 里钉着的自签证书 SAN 就是服务器公网地址 | 否决：发一次包等于把服务器地址公开一次，直接撞 writing-rules §9；改私有 release 又要多管一套访问令牌，比两条路由贵 |
| 蒲公英 / Firebase App Distribution 这类分发平台 | 包和版本说明都要上传到别人服务器，还要引它们的 SDK | 否决：ADR-0009 已经否过"把访问入口交给第三方控制面"，这条把包也一并交出去；ADR-0010 又明确不引这类库 |
| 客户端静默自装（Device Owner / root 权限） | Device Owner 只能靠 adb 或恢复出厂设置预置，root 不是可依赖前提 | 否决：为省一次点击要把手机交出去做特殊配置，代价和风险都不对；Android 的安装确认本来就是设计意图 |
| 不做提醒，只留一个手动下载链接 | 零代码 | 否决：更新不及时在这套系统里有实际代价——服务端接口一改，旧客户端只会报错，需求方自己说的"不提醒就会长期不更新"是这条否决的全部理由 |

## 影响

- **得到**：手机上能收到更新提醒并一次点完下载与安装；不开新端口、不引新依赖、不把包或地址交给任何第三方；`versionCode` 成了唯一的发版凭据，不用另建版本表。
- **付出**：服务端多一个放包的目录和两条路由；APK 约 10 MB 量级，走 8443 下载要按服务器带宽等一会儿；发版流程多一步拷贝；换 keystore 就得卸载重装一次；`/v1/app/release` 也要口令，所以更新检查只在已经连上过之后可用（全新安装本来就该是最新版，不构成死锁）。
- **返工点**：改走 Play 只需把检查/下载那段换成 In-App Update SDK，release 接口留着不动；改走对象存储只把 `url` 的来源换掉，服务端两条路由删掉即可——都不动数据模型和业务接口。
- **连带决定**：`versionCode` 每次发版必须加 1（现在写死 1），否则覆盖安装失败；release 目录不存在或未配置时接口回 404，客户端静默不提示，不算错误；口令与 keystore 一律不进仓库、不进对话记录以外的公开场合；`ProtectSystem=strict` 的沙箱不变，包目录放在已经可写的 `/var/lib/memora` 下；第一次更新要多开一个系统开关——Android 8 起"允许安装未知应用"按来源逐个授权，撞上去只会得到一句"For your security…"，所以客户端先查 `canRequestPackageInstalls()`，没允许就把人送到那个开关前面而不是硬跳安装页。

## 复查条件

出现以下情况时重新评估本决策：

- 需要给第二台设备或第二个人分发 → 重谈 Play 内测轨道或私有分发
- APK 体积大到下载成为日常负担（几十 MB 以上），或公网流量费用明显起来 → 把包挪到对象存储，只保留版本查询接口
- 需求方拿到域名并换成 CA 证书（ADR-0009 的复查条件同时触发）→ 更新通道跟着换地址，逻辑不动
- 出现"必须无人值守更新"的真实需求 → 只有 Device Owner 一条路，届时整条重开

## 替代成本参考

同类自用 Android 应用的常见做法是 GitHub Releases 配一个自研检查页，或自建 F-Droid 仓库。前者在公开仓库场景下会把内置证书里的地址一起发出去，后者要维护 repo 签名与索引，两条都比"服务端两条只读路由 + 客户端一次比对"贵。
