# ADR-0008：安卓端用 Kotlin + Compose，自签 APK 不上架

> 状态：生效中
> 摘要：原生 Kotlin + Compose 写列表、录入、报表查看三块界面，产物是自己装的 APK；不引跨端框架，也不走 PWA
> 日期：2026-11-24 ｜ 关联：[0001](0001-server-owned-data-on-lan.md)、[0006](0006-go-single-binary-server.md)

## 决策

客户端用原生 Kotlin + Jetpack Compose，网络层用 OkHttp/Retrofit。界面就三块：记录列表（含关键词过滤）、输入/编辑页、报表查看页（带复制）。产物是自签的 APK，需求方手动装到手机上，不走应用商店。

## 背景

需求是"手机软件，安卓的备忘录，只要简单功能"。选型时已明确：Android Studio 装在需求方自己的电脑上，装不到这台服务器；服务端已定为 Go（ADR-0006），所以客户端选什么语言都拿不到"全栈一门语言"的好处。

## 备选方案

| 方案 | 主要代价 | 结论 |
| --- | --- | --- |
| **原生 Kotlin + Compose** | 需要一台能跑 Android Studio 的机器；只覆盖安卓，将来出 iOS 要另写 | **采纳** |
| Flutter / React Native | 多一层工具链、桥接层，版本升级被框架节奏绑住 | 否决：跨端能力在"只发给自己用的安卓"这个范围内一次都用不到，但构建链复杂度从第一天就全额支付 |
| PWA（服务端多出一个移动端网页） | 通知与后台能力弱，不是"真应用" | 否决（本轮）：需求方明确要安卓应用。**但这是本项目工作量最小的一条路**——如果后面不想维护两套代码，应该新开一条 ADR 正面推翻本条，而不是悄悄把重心挪过去 |
| WebView 壳套自己的网页 | 打包成 APK 但内容还是网页 | 否决：拿不到原生输入体验，却要背下 APK 签名、打包、安装的全部麻烦，两头好处都没落到 |

## 影响

- **得到**：一个真 APK；输入法行为、剪贴板复制、通知这些细节都是原生的——对一个以文字录入为核心的应用，输入法手感不是小事。
- **付出**：两套代码、两种语言要各自维护和各自出包；每次界面改动都要重新编译 APK 装到手机；服务器地址和访问口令要存在手机上。
- **连带决定**：口令在客户端必须进系统 Keystore 加密保存，不能落明文偏好文件——因为 ADR-0002 里整个访问控制就靠这一串字符，它躺在明文文件里等于把防线交出去。另外 [ADR-0001](0001-server-owned-data-on-lan.md) 定了不做离线，但需求 §5 那条"未提交的输入不该整屏丢掉"仍然要客户端自己兜住（进程被杀前留一份草稿）。
- **返工点**：若改 PWA——客户端整块消失，服务端要多一套页面；数据层和接口契约都不用动。

## 复查条件

出现以下情况时重新评估本决策：

- 需求方不想再维护独立的安卓端 → 直接重谈 PWA
- 需要覆盖 iOS 或其他设备 → 这时跨端才第一次成为真需求
- 需要后台定时提醒一类能力，且实测确认 PWA 在安卓上确实做不到
