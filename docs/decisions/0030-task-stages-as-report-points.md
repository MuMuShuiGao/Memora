# ADR-0030：长待办挂阶段，阶段完成即进周报

> 状态：生效中
> 摘要：`tasks` 下挂最多 5 个阶段（一句话 + 一个勾 + 可选 50 字心得）；阶段勾掉即按那一刻进报表，不排日期、不进日历、不占名次、不能嵌套；否掉子任务化、父任务完成时汇总、用记录写进展
> 日期：2026-11-28 ｜ 关联：[design/memo-and-report.md](../design/memo-and-report.md)、[design/android-client.md](../design/android-client.md)

## 决策

新增 `task_stages`，给待办挂一层最多 5 个阶段的短标题：一句话（≤30 码点）+ 完成态 + 可选完成心得（≤50 码点，与待办同口径）。阶段是**汇报点**而不是子任务：勾掉一个阶段，它就以父任务的名义进入那一期的报表素材，措辞是"推进/完成了某阶段"，不是"交付整个任务"。阶段不排日期、不进日历、不占待办名次、不参与拖拽、不能嵌套；父任务与阶段的勾选互不门控。客户端入口只在待办的行内编辑态（「＋ 加阶段」），没加阶段的待办界面零变化；有阶段的任务平时只多一行「下一步：<第一个未勾阶段>」。

本条把 [projectneed.md §2](../projectneed.md)「不做」里的"子任务"改写成"阶段的日期、嵌套与排序"，只引入汇报点，不引入任务管理。部分修订 [ADR-0014](0014-todo-tasks-with-priority.md) 与 [ADR-0021](0021-calendar-dated-tasks.md) 的复查条件（原文把"子任务"视为应该另起系统的信号）。

## 背景

- 报表只收本周期内勾掉的待办（ADR-0014、FR-11）。一个跨三四周的长任务，中间几周的周报里完全隐形，最后一周只剩一行"完成 X"；过程中推进了什么，没有任何素材。
- 需求方 2026-11-28 要"像职场分阶段汇报"：长待办中间能分段，每段做完能在当周周报里写一句；同时明确短待办不需要，界面不能被拖复杂。
- 约束：记录、待办、读书已是三类互不转换的对象；客户端只依赖 OkHttp + kotlinx.serialization（ADR-0010）；服务端 SQLite 幂等建表（ADR-0007）；单人使用，不做冲突处理。
- "没做完的不进报表"是 FR-11 的红线，阶段方案必须保住它——只有勾掉的阶段才进周期。

## 备选方案

| 方案 | 主要代价 | 结论 |
| --- | --- | --- |
| 阶段作为待办下的汇报点，独立成表 | 新表 + 三个接口 + 一段行内界面 | **采纳** |
| 把长任务拆成多条独立待办（"X：阶段一"） | 不新增表与接口 | 否决：占多个名次、互相竞争排序，看不出同属一件事；父任务收尾还要另立一条 |
| 让未完成的阶段或进展直接进报表 | 中间周的问题一次解决 | 否决：推翻 FR-11，报表会把半成品说成交付，"不许编造"的核查抓手也跟着失效 |
| 阶段只在父任务完成时汇总进那一周的报表 | 不用给阶段开归属列 | 否决：中间几周仍然空白，正是本次要解决的问题 |
| 阶段带自己的日期、进日历、可拖拽排序 | 更接近任务系统 | 否决：日历与名次都长出第二套语义；阶段是汇报点，不是可独立排期的任务 |
| 阶段没勾完不许完成父任务；全勾完自动完成父任务 | 语义更严 | 否决：前者挡住"勾一下就完成"（FR-09），后者替用户宣布项目交付，报表会凭空多一份没声明的交付 |
| 不建阶段，长任务期间用记录每周写一句进展 | 零改动 | 否决（暂缓）：进展以"想法"而非"阶段完成"进素材，与任务没有从属关系，还得自己记得写；留作复查时的退路 |
| 每个待办行常驻展开箭头 | 更容易发现 | 否决：短待办占绝大多数，常驻箭头违反"零打扰"；入口藏在行内编辑态即可 |

## 影响

- **得到**：长任务每周都有已完成的阶段可写；父任务仍保持"一件事"的归属；心得机制原样复用；短待办零变化。
- **付出**：`GET /v1/tasks` 每条待办多带 `stages`；待办屏多一种折叠行与展开态；报表素材多一路，提示词要防"同周父任务与阶段都完成"时的重复叙述；传输与存储量可忽略（每条 ≤5 个阶段，估算）。
- **返工点**：一旦阶段要自己的日期、提醒、嵌套或百分比，它就成了任务管理对象，`task_stages`、日历、排序与报表取数要一起重写（ADR-0014、ADR-0021 的复查条件同时触发）。
- **连带决定**：阶段按加入顺序排，不做拖拽；删除待办时同事务删掉它的阶段；已完成待办保留阶段并可展开，仍可补勾、补改心得，但不再加新阶段；阶段没写心得时报表不得替它补结果；候选周期要算上"只勾了阶段"的那一周；`source_count` 把阶段算作素材条数。

## 复查条件

出现以下情况时重新评估本决策：

- 需求方要求阶段带日期、提醒、嵌套、排序或完成百分比——那时它已是任务系统，要重估整个待办的定位。
- 实际使用中绝大多数阶段只有 1 个，或阶段心得长期不写——阶段退化成纯打勾，重估是否收回功能、回到"用记录写进展"。
- 一条任务的阶段长期全部勾完、父任务却迟迟不勾——重估"父任务完成"与阶段收尾的关系，可能需要一次收尾提示。
- 出现"补勾阶段导致报表错位"的抱怨——重估完成时刻按勾掉时间还是实际做完时间。

## 替代成本参考

Things、Todoist 的 checklist 项只是任务内部清单，不产生可汇报的产出；Asana 的里程碑、Jira 的版本节点才是"完成一个节点 = 可以对外说一句"的单位。周报工具（iDoneThis、Geekbot）以"本周做了什么"为单位，同样不要求每件事干完。本条取里程碑语义，但不引入依赖关系与排期。
