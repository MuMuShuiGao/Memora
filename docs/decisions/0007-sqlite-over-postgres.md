# ADR-0007：数据层用单文件 SQLite，不用机器上现成的 PostgreSQL

> 状态：生效中
> 摘要：记录和报表存在服务端一个 SQLite 文件里（WAL），备份就是复制该文件
> 日期：2026-11-24 ｜ 关联：[0001](0001-server-owned-data-on-lan.md)、[0006](0006-go-single-binary-server.md)

## 决策

备忘录记录和生成的报表快照都存在服务端一个 SQLite 数据库文件里，开 WAL 模式让读不阻塞写。库文件路径走服务端配置项。备份方式是复制这个文件，不需要任何数据库服务、角色或转储工具。

## 背景

[ADR-0001](0001-server-owned-data-on-lan.md) 定了权威副本在服务端，但没定用什么存。本机已装 PostgreSQL 17，`createdb` 和 `pg_dump` 实测可用。当时手上的选择是"用现成的 PG"和"用单文件库"。数据规模预期很小：一个人随手记，按日均几条估算，一年也就千条量级。

## 备选方案

| 方案 | 主要代价 | 结论 |
| --- | --- | --- |
| **SQLite 单文件（WAL + 纯 Go 驱动）** | 写是单写者；没有 PG 的迁移工具生态 | **采纳** |
| 复用已装的 PostgreSQL 17 | 应用要依赖一个必须活着的服务：建库建角色、管连接串和连接池、单独安排 `pg_dump`、PG 挂了整个应用一起挂 | 否决："已经装好了"不是技术理由。给一个单人单进程的读写引入独立数据库服务，换来的是运维面而不是新能力，而这个项目一条额外能力都不需要 |
| 直接存 JSON / 行文本文件 | 零依赖 | 否决：FR-03 的关键词过滤和 FR-04 的"取某周期内的记录"都是查询，靠扫文件等于自己手写一套糟糕的索引，还得自己保证写入不损坏 |
| 换现成后端（PocketBase 一类） | CRUD、鉴权、定时都白送 | 否决：它把口令校验（ADR-0002）、定时生成（ADR-0004）、模型调用（ADR-0003）三件事全塞进它自己的扩展机制里，出问题时调试路径变成"先查它的钩子怎么挂的"；同时被绑定它的存储。省下的那点脚手架，不值得把三处核心逻辑寄在别人模型里 |

## 影响

- **得到**：备份与迁移都是复制一个文件；不占常驻内存和端口；服务启动不依赖任何外部可用性——这正好接住需求 §5 里"模型不可用时记录仍可读"那条约束（库在自己手里就一定能开）。
- **付出**：并发写受限（单写者，WAL 只缓解读写互斥）；类型约束比 PG 松，靠表定义和代码保证；库文件会随报表快照一起长大（估算每份报表几 KB，长期可忽略）。
- **返工点**：真要换 PG——SQL 大部分方言兼容，主要工作是连接管理、provisioning 和迁移工具。如果 `design/` 里把数据访问收在一层，改动集中在那一层；没收散就到处都是。
- **连带决定**：备份策略变成"有没有人在定期拷这个文件"——这件事目前没有任何机制保证，需要单独决定怎么落（见 NOW 待确认）。

## 复查条件

出现以下情况时重新评估本决策：

- 有第二个进程需要同时写同一个库文件
- 记录或快照数量涨到复制文件做备份明显变慢（先按万条这条线估算，到跟前再实测）
- 需要只有 PG 才提供的能力（全文检索、并发的密集读、跨表事务外的复杂约束）
