# ADR-0002：只做单个访问口令，不建账号体系

> 状态：生效中
> 摘要：服务端存一个访问口令，客户端记住它；不做注册、登录态管理与用户维度
> 日期：2026-11-24 ｜ 关联：[../projectneed.md](../projectneed.md) FR-07、[0001](0001-server-owned-data-on-lan.md)

## 决策

服务端配置里放一个访问口令，客户端首次使用时输入一次并记住，之后每个请求带上它。校验失败就拒绝读写。没有注册、没有"用户"这个概念，所有数据天然属于唯一的使用者（就是需求方本人）。

## 背景

需求方明确表示"只有我自己用"。但"单人"和"无鉴权"不是一件事：服务监听在私网地址上，同网络内可能有别人的设备；而将来任何一次端口暴露都会让全部记录可被读到。所以要选的是用什么凭证挡人，不是要不要挡。

## 备选方案

| 方案 | 主要代价 | 结论 |
| --- | --- | --- |
| **单个固定访问口令，客户端记住** | 无法区分"是谁访问的"；口令泄露即全部内容泄露；换口令要在服务端和手机上各做一次 | **采纳** |
| 完整注册 / 登录 / 找回密码 | 邮箱或短信验证通道、密码哈希与重置流程、按用户隔离数据、每一个查询都要带归属条件 | 否决：本项目的真实问题里没有一个是账号体系能解决的，它只增加攻击面、外部依赖和长期维护量 |
| 单人起步，但表和接口先预留 user_id | 每张表多一列、每个接口多一层归属过滤，从第一天起所有查询都带上"这个人的"条件 | 否决：为一个还没出现的用户提前付结构性成本，而"所有查询都要带归属"这个心智负担立刻生效。真到多人那天，加一列并回填是一次可控迁移，不构成需要现在预埋的理由 |
| 完全不做鉴权，依赖"内网进不来" | 零成本 | 否决：私网不等于自己人；且这条会让 ADR-0001 里"以后可以上公网"的复查条件提前失效，等于把出口焊死 |

## 影响

- **得到**：鉴权逻辑就是一次字符串比对，客户端也不需要有会话、刷新、登出这些状态。
- **付出**：换设备要重新输一次口令；口令本身强度全靠需求方自己选；无法审计访问来源。
- **返工点**：真要变成多用户——需要新增用户与凭证存储、给现有全部记录回填归属、客户端加登录页与会话管理。数据层改动小，接口层基本要过一遍。
- **连带决定**：口令必须走 HTTPS 之外的第二道防线已经没有了，所以本条与"不开公网"（[0001](0001-server-owned-data-on-lan.md)）是绑定的。把服务挪到公网必须新开一条 ADR 重谈鉴权。

## 复查条件

出现以下情况时重新评估本决策：

- 出现第二个真实使用者，或需要把不同人的记录分开
- 服务需要暴露到私网以外
- 记录内容开始包含不宜被同网络他人读到的信息（此时口令这一层不够）

## 替代成本参考

同类自用小工具普遍做法是反向代理加 Basic Auth 或一个静态 token 头。本项目把校验放进应用自身，是为了不额外依赖一个组件——代价是要自己写清"口令错误时不返回任何数据"这条边界（FR-07 的验收线）。
