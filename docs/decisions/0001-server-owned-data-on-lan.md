# ADR-0001：数据权威副本放在服务器，客户端不做本地主库

> 状态：生效中
> 摘要：手机直连私网服务器读写，服务器上的副本就是唯一真相；离线记录与补交暂不做
> 日期：2026-11-24 ｜ 关联：[../projectneed.md](../projectneed.md) FR-01、FR-02

## 决策

备忘录内容和生成的报表都以服务器上的副本为准。安卓端不落一份自己的主数据，只在打开时向服务器读、保存时向服务器写。服务器只在私网可达（本机有一个内网私网地址，实测；无域名、80/443 无监听），手机离开这个网络就用不了应用——这是接受的代价，不是待修的缺陷。具体地址值不入文档，见 [../writing-rules.md](../writing-rules.md) §9 关于标识值不落档的禁令。

## 背景

需求方说"数据存在当前服务器中，只要简单功能"。这台机器现有 PostgreSQL 17 与 Docker，无公网域名。真正需要回答的是"哪一份数据算数"：一旦手机端也有一份，且允许各自变化，就必须回答冲突怎么办。

## 备选方案

| 方案 | 主要代价 | 结论 |
| --- | --- | --- |
| **服务器为唯一权威副本，手机直连私网读写** | 不在该网络时整个应用不可用；每次保存有一次网络往返 | **采纳** |
| 手机本地为主库，服务器只做备份与换机找回 | 要判断"哪份是真的"：多端写冲突、时间戳不可信、备份落后于本地时找回会静默丢记录 | 否决：换机/重装是低频事件，却要用天天承担的冲突逻辑来换；而且"备份落后"这种失败模式是静默的，比不能访问更糟 |
| 离线优先：本地暂存 + 联网后自动补交队列 | 要写操作队列、幂等标识、冲突策略、"待同步"状态提示 | 否决（当前阶段）：这块的工作量与本项目其余部分加起来同量级；"不在私网时最想记"的场景确实覆盖不到，但先用 FR-01 的验收线证明需求真实存在，再决定是否为它换数据层 |
| 走公网 HTTPS，让手机在任何网络都连得上 | 需要域名解析、证书申请与续期、反向代理，且服务真的暴露到公网，访问口令成为唯一防线 | 否决：手上没有域名（本次对齐已确认），而一个人用的工具不值得开公网增加暴露面 |

## 影响

- **得到**：数据只有一份，没有冲突语义要定义；换手机只需填对地址和口令即全部找回；报表产物、生成历史也天然归到服务端，定时任务不依赖任何设备在线。
- **付出**：私网外不可用；弱网下保存有可感等待；服务器宕机期间无法记录；手机端不留底，**正在输入但尚未提交**的内容有丢失风险，这一点必须在客户端单独兜住（见需求 §5 第 3 条）。
- **返工点**：若日后改成离线优先——客户端要加暂存层与待提交队列，服务端写入接口要接受客户端生成的幂等标识（否则补交会重复），列表要区分"已存"与"待同步"。是在现有读写之上加层，不需要推翻数据归属结论。
- **连带决定**：报表生成只能由服务端调模型，不能放手机端（否则离线补交与定时任务都无处落脚）——见 [0003-external-llm-generation.md](0003-external-llm-generation.md)。

## 复查条件

出现以下情况时重新评估本决策：

- "不在私网却必须记一笔"真实发生到每周数次，说明离线不是边缘场景
- 保存/读取的往返等待在日常使用中明显到影响"随手记"的意愿
- 需要让第二套部署或另一个人访问同一批数据
- 拿到了域名、愿意接受公网暴露，此时网络接入这一半应该单独新开一条 ADR

## 替代成本参考

成熟的离线优先方案（本地嵌入式库 + 变更日志同步，如 CouchDB/PouchDB、RxDB）已经把冲突与补交实现好了，但引入其中之一等于替换整个数据层和读写模型，与"只要简单功能"的初衷不成比例。
