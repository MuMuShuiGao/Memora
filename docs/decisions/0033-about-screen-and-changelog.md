# ADR-0033：抽屉底部「关于」入口与本地更新记录

> 状态：生效中
> 摘要：抽屉底部加一行「关于」，点开独立关于屏——版本号、检查更新与写死在包里的更新记录；不加服务端接口，发版时顺手补一条
> 日期：2026-11-28 ｜ 关联：[android-client.md](../design/android-client.md)、[ADR-0015](0015-self-hosted-apk-release-channel.md)、[ADR-0028](0028-left-drawer-navigation.md)

## 决策

主屏抽屉底部隔一道发丝线加一行「关于」，右侧淡墨写当前版本；点开一屏独立的关于页（盖住主屏，与更新页同级）。关于页三段：身份（Memora、`v版本名（版本号）`、本地构建标记）、版本更新（复用 `UpdateChecker` 的状态，可手动检查，有新版本跳更新页）、更新记录（`Changelog.kt` 里写死，从 v0.9 起逐版列，0.1–0.8 合并成一行）。不新增服务端接口，不动更新通道契约（ADR-0015）。

## 背景

- 需求方的方向是「侧边栏最下面或者新建一个关于，模仿主流 app，里面记录版本升级相关的」；更新记录的收录范围定为从 v0.9 起，更早的合并一句。
- 现在版本号只在更新页一闪而过，而更新页只有"服务端有新版"时才进得来；平时没法确认本机装的是哪版、这版改了什么。
- 服务端 `release.json` 只描述最新一版，没有历史，也不该为静态文本扩成列表——更新记录应该跟着安装包走，离线也能看。
- 客户端不引新依赖（[ADR-0010](0010-minimal-android-deps.md)），检查更新与下载安装已由 `UpdateChecker` 提供，关于页只做入口与展示。

## 备选方案

| 方案 | 主要代价 | 结论 |
| --- | --- | --- |
| 抽屉底部入口 + 独立关于屏 + 本地写死更新记录 | 每发一版要手动补一条；多一屏 | **采纳** |
| 「关于」作为抽屉第七个区块 | 目录里混进一个非日常功能区 | 否决：关于不是内容区块，混进待办/日报同一张目录里会误导点击；需求方原话也是"最下面" |
| 关于内容并进更新页，不新开屏 | 少一屏 | 否决：更新页是一条动作流程（检查—下载—安装），历次记录塞进去会把"要不要更新"淹掉；而且没有新版时那页根本进不来 |
| 服务端提供版本历史（扩 `release.json` 或新接口） | 记录可远端维护、补录不用发版 | 否决：为一个静态列表改更新通道契约、加部署同步步骤，离线还看不到；历史记录本来就该跟包走 |
| 每次更新后弹一次"更新说明"对话框（主流做法） | 不占常驻入口 | 否决：弹窗看过即走，需求要的是"能随时翻看"；本项目也约定"打开就弹一屏"违反两次点击进键盘 |

## 影响

- **得到**：版本号、手动检查更新与历次更新记录收在一页；抽屉底部多一个稳定的落点，以后隐私、许可之类条目有地方放。
- **付出**：发版清单多一步——`Changelog.kt` 顶部补一条并与 `versionName` / `versionCode` 对齐，漏补是文档问题、界面不报错；关于屏多一屏要维护；更新记录从 v0.9 起，更早的只留一行概述。
- **返工点**：若以后要远端维护公告或强制更新，把 `Changelog.kt` 换成接口数据源即可，关于屏版式不动；抽屉底部入口若要改成一个"设置"聚合页，只动 `MemoraDrawer`。
- **连带决定**：关于不算区块，不进 `SECTIONS`、不参与 `rememberSaveableStateHolder`；自动检查更新仍是进主屏时一次（ADR-0015），关于页的手动「检查更新」复用同一个 checker，不新增轮询。

## 复查条件

出现以下情况时重新评估本决策：

- 更新记录与实际版本脱节：连续两个版本忘了补，说明手动维护这条路不成立，改接口下发。
- 关于页内容扩到多语言、隐私政策、许可清单等需要滚很长的条目，单屏放不下——改为并入设置页，而不是继续往下堆。
- 抽屉条目多到需要分组时，重新看底部入口的位置。

## 替代成本参考

主流 Android 应用普遍把"关于/设置"放在抽屉底部或溢出菜单，页内以"版本号 + 检查更新 + 更新日志"三段为主。更新日志多数由应用商店渠道托管；自托管分发没有商店，跟随安装包内置更新记录是最常见的做法（F-Droid 上的应用普遍在包内带 changelog）。
