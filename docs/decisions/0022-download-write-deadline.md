# ADR-0022：更新包下载单独放宽写期限

> 状态：生效中
> 摘要：APK 下载这一条响应把 HTTP/2 的单流写期限放宽到十分钟，全局 `WriteTimeout` 仍是 60 秒；日志包装层补 `Unwrap` 让 `ResponseController` 能穿透
> 日期：2026-11-27 ｜ 关联：[ADR-0015](0015-self-hosted-apk-release-channel.md)、`internal/api/release.go`

## 决策

`GET /v1/app/release/file` 在写出响应头前，用 `http.NewResponseController(w).SetWriteDeadline(now+10m)` 把这一条流的写期限单独放宽到十分钟。`http.Server.WriteTimeout` 保持 60 秒不变，其余接口照旧受它约束。配套把访问日志的 `statusRecorder` 补上 `Unwrap() http.ResponseWriter`，否则 `ResponseController` 穿不过这层包装，`SetWriteDeadline` 只会静默返回 not supported。

## 背景

v0.5 发布后真机更新失败，更新页显示 `stream was reset: INTERNAL_ERROR`。云机日志里两次下载都是整 60 秒结束（`took=1m0.976s`、`took=1m0.236s`），状态 200——头已发出、正文没写完。Go 的 HTTP/2 服务端把 `Server.WriteTimeout` 同时当作每条流的写期限，超时后向该流发 `RST_STREAM(INTERNAL_ERROR)`；OkHttp 把收到的重置原样报成上面那句。客户端读超时是 90 秒，不是它先断的。

包本身约 7.6 MB，手机走蜂窝网在这个实例上拉不完一分钟。HTTP/2 的流控窗口让服务端在客户端读得慢时阻塞在写上，写期限一到就被重置。

## 备选方案

| 方案 | 主要代价 | 结论 |
| --- | --- | --- |
| 下载响应单独设十分钟写期限 | 多一行代码；需要日志包装层实现 `Unwrap` | **采纳** |
| 把全局 `WriteTimeout` 提到十分钟 | 所有慢接口都跟着放宽，挂住的普通请求占用连接更久 | 否决：只有下载是"越长越正常"的响应，别的接口没有理由宽限 |
| 全局关闭写超时 | 任何半开连接都能永久占住 fd | 否决：公网端口上等于自拆一条防线 |
| 单独再起一个文件服务/端口发 APK | 不改主服务的超时模型 | 否决：第二套监听、证书、口令与防火墙规则，把 ADR-0015「同端口同口令」的简化全推翻 |
| 客户端按 Range 小段续传多次请求 | 单次请求不易超时 | 否决：把服务端缺陷转成客户端复杂度，还要处理合并与校验，问题只是被拆小 |
| 下载改走 HTTP/1.1 | 避开 h2 的流重置语义 | 否决：同一超时也会在 HTTP/1 上直接断连接，症状换个样子；且按路由强制协议没有现成开关 |

## 影响

- **得到**：慢速网络也能把包拉完；真机那条错误消失。十分钟仍是有限期限，完全停滞的下载最终会被放弃。
- **付出**：`statusRecorder` 多一个 `Unwrap`；下载这条路径的写超时不再与全局一致，读代码时要意识到这处例外。
- **返工点**：若 APK 涨到十分钟也拉不完，得改成断点续传为主、单次请求限时；若以后报表导出等也走大文件下载，应把这条响应级超时收成一个公用函数。
- **连带决定**：回归测试 `TestReleaseDownloadSurvivesSlowClient` 用 HTTP/2 + 300ms 写超时 + 慢读复现原症状；去掉放宽那行就会红。

## 复查条件

出现以下情况时重新评估本决策：

- APK 体积或最慢网络组合超过十分钟（例如包到 50 MB 以上）。
- Go 调整 `WriteTimeout` 在 HTTP/2 下的语义，或 `ResponseController` 的穿透规则变化。
- 出现第二类大文件下载（报表导出、备份），需要统一策略。

## 替代成本参考

静态文件服务普遍给下载单独设更长的超时，或在反向代理层把缓存/限速接走；本仓库没有反向代理，单二进制直接对外，所以只能在响应级开口子。nginx 一类默认对静态文件不设这么短的写超时，也是同一个道理。
