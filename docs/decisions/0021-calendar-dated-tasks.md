# ADR-0021：待办带安排日期，日历和待办页看同一张表

> 状态：生效中
> 摘要：`tasks` 增加自然日 `due_on`；待办页列全部，日历按天看同一批待办，在日历某天加的条目照样进待办页；不另建日历表，不做提醒、重复、子任务
> 日期：2026-11-27 ｜ 关联：[design/memo-and-report.md](../design/memo-and-report.md)、[design/android-client.md](../design/android-client.md)

## 决策

给 `tasks` 加一列 `due_on`（`YYYY-MM-DD`，服务端本地时区的一个自然日）。客户端新增「日历」页签：月视图按 `due_on` 把**同一批待办**分到每一天，选中某天就在那一天下方录入；新建时把选中的日子作为 `due_on` 发出去，因此它立刻出现在待办页——两页没有第二份数据，也没有同步逻辑。待办页新建不指定日期时按服务端本地时区的「今天」落，这样所有待办都能在日历上找到自己的位置。旧行在升级时按 `created_at` 的本地日期回填一次。

日历页只做两件事：**在某天加一条**、**勾掉某条**。改文字、拖顺序、删除仍只在待办页做——把那些手势和确认态复制一份到月网格里，两个屏会各自长出一套状态机，而它们本来就共用同一条服务端路径。日期也不参与报表归属：报表仍只看 `done_at`，这条不变。

本条部分修订 [ADR-0014](0014-todo-tasks-with-priority.md) 的复查条件（原文把"需要截止日期"视为应该另起系统的信号）和 [projectneed.md §2](../projectneed.md) 的"不做截止日期"。只引入日期，不引入提醒、重复、子任务，随手记的录入成本不增加。

## 背景

需求方要一个日历：第一个页面是所有待办，第二个页面按天记录 todo，在日历里加的要进第一个页面。现有待办是一列有优先级和完成态的条目（ADR-0014），没有任何时间维度，日历无从分栏；而两页必须同源，否则「日历加的会加到待办页」只能靠客户端复制/合并，迟早对不上。

已有限制：客户端只存口令、地址、草稿等五样，不缓存业务数据（ADR-0001）；服务端 SQLite 单文件、启动时 `CREATE TABLE IF NOT EXISTS` 幂等建表（ADR-0007）；客户端不引日历库（ADR-0010）。

## 备选方案

| 方案 | 主要代价 | 结论 |
| --- | --- | --- |
| `tasks` 加 `due_on`，日历是它的按天视图 | 多一列、多一个页签；日期只有天，没有时分 | **采纳** |
| 另建 `calendar_entries` 表，与待办互相对拷 | 同一条事有两份行，勾选、改字、删除都要双向扇出；任何一次失败都制造两个真相 | 否决：同步逻辑本身就是这类需求最容易坏的地方，能不引入就不引入 |
| 把日历建在 `notes` 上 | 记录没有完成态与优先级，要给一批「记录」另外挂勾选，等于把待办语义复制进流水表 | 否决：两张表的边界（ADR-0014）就是为了不让这件事发生 |
| 日期只存手机本地 | 不动服务端，一天能出 | 否决：换手机、另一台设备、日历与待办页之间都会分叉，直接违背 ADR-0001 |
| `due_on` 允许为空，日历只显示有日期的 | 老的、随手记的待办不进日历，改动最小 | 否决：需求方要的是「所有待办」和日历同源；留一堆永远不上日历的条目，等于两页各看一半 |
| 日期精确到时分并加系统提醒 | 更接近传统日程 | 否决：要闹钟/通知权限、后台调度与跨时区规则，本次需求没有提；先把「哪一天」做对 |
| 引第三方日历组件 | 网格不用自己画 | 否决：ADR-0010 把依赖钉死在 OkHttp + kotlinx.serialization；一个 6×7 的月网格是一屏自绘代码，换来版式完全贴合「编辑部案头」 |

## 影响

- **得到**：两页共用 `GET /v1/tasks` 的全量数据；在日历上写的一句，切回待办页就是同一条，不需要额外的「同步」接口或冲突策略。日历还是完成记录：勾掉的条目仍留在它那一天，带删除线。
- **付出**：`tasks` 多一列并要回填历史行；创建接口多一个可选字段；待办页的每行多一行日期标注（只标非今天，避免刷屏）；日历上不能改字/删除，需要切到待办页。
- **返工点**：若以后要提醒、重复、子任务或时分精度，`due_on` 这一列不足以承载，得引入日程对象与通知调度，日历屏和接口都会重写；若待办量超出现有 500 条全量安全上限，`GET /v1/tasks` 要加按月过滤。
- **连带决定**：日期按服务端本地时区解释，与报表口径同一个时区来源；客户端选日时直接发 `YYYY-MM-DD`，不做时区换算——手机与服务端时区不一致时，以手机所选的字面日期为准，这是单人单时区使用的取舍。

## 复查条件

出现以下情况时重新评估本决策：

- 需要提醒/通知、重复任务、子任务、跨天事件或时分精度——日历要变成真正的日程系统。
- 不止一个人使用，或设备分布到不同时区（ADR-0002 失效）。
- 待办量长期超过 500 条，一次全量返回变得不合理。

## 替代成本参考

Things、滴答清单这类产品同样把「清单」和「日历」当作同一批任务的两个视图，日期是任务上的一个属性，而不是另一张表。差别在它们有提醒与重复；本条明确停在没有提醒的那一步。
