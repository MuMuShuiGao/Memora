# ADR-0029：读书清单独立成表，读完月份 + 一句心得

> 状态：生效中
> 摘要：`books` 独立成表，字段是书名/作者/读完年月/心得；按年分组翻看，不进周报月报；否掉并入记录、精确到日、只记年份与评分在读
> 日期：2026-11-27 ｜ 关联：[design/memo-and-report.md](../design/memo-and-report.md)、[design/android-client.md](../design/android-client.md)

## 决策

读书清单是第三类业务对象，单独一张 `books` 表：`title`（必填）、`author`（可空）、`finished_month`（`YYYY-MM`，默认手机当月）、`takeaway`（一句心得，可空，≤200 码点）。界面按年分组、年内按读完月份倒序；加书走屏顶一条输入，改书名/作者/月份、补删心得走书编辑页。读书数据**不进入周报月报素材**，与记录、待办互不转换。

## 背景

- 需求方要「记录我读过的书，读完有什么心得，按年为单位」，明确只做这两件事，界面要简约。
- 记录与待办都已独立成表（[ADR-0014](0014-todo-tasks-with-priority.md)）：记录按创建时间进报表，待办带完成态与顺序，两边的归属口径不同。书没有完成态，也不该进工作报表。
- 数据必须落在服务端（[ADR-0001](0001-server-owned-data-on-lan.md)）：换手机后书单要完整找回，客户端不缓存业务数据。
- 需求方定的是「记到月，xx 年 xx 月读完就好」，不要精确到日。

## 备选方案

| 方案 | 主要代价 | 结论 |
| --- | --- | --- |
| `books` 独立成表，读完记到月，心得可后补且不进报表 | 新表、四个接口、两屏界面 | **采纳** |
| 并入 `notes`，加一个类型标记或标签 | 不用新表 | 否决：记录会整批进周报素材，书单混进去等于每月把书名喂给工作报表；再加过滤列，等于在流水表上重建一张书表 |
| 读完时间精确到日 | 排序更细 | 否决：需求方只要年月；精确到日还得处理日期选择与时区，收益只是同月内的先后 |
| 只记年份 | 最简单 | 否决：需求方要看到「xx 年 xx 月读完」；只记年也补不回月份 |
| 心得沿用待办的 50 字上限 | 与现有心得同一口径 | 否决：书的心得是一段完整的想法，50 字写不下；另开 200 码点的上限，待办那条不动 |
| 增加在读状态、评分、封面、豆瓣导入 | 更像读书产品 | 否决：本次只要「读过的书 + 心得」；这些会把随手记录变成图书管理，见需求「不做」表 |
| 读书心得也进周报月报 | 素材更丰富 | 否决：周报月报是工作口径，读一本书不等于一份交付；混进去会稀释报表 |

## 影响

- **得到**：书单有独立的增长空间，按年翻看；备份快照自动覆盖 `books`，不增加运维动作。
- **付出**：服务端多一张表、多四个接口；客户端多两屏；书名/作者/月份/心得四个字段在 PATCH 里按字段更新，比记录的单正文多一套校验。
- **返工点**：若以后要评分、在读状态或读完日期精确到日，`books` 加列即可，界面与接口的字段校验要同步；若要把书进报表，需在提示词与素材查询里另开一路，且要重新定义「书算什么」。
- **连带决定**：心得可清空（空串等于没写）；删除书是显式动作，不做软删除；读书页不做搜索与分页（一年几十本，全量拉取），安全上限 1000 条。

## 复查条件

出现以下情况时重新评估本决策：

- 需求方要评分、在读进度、阅读日期区间、封面或外部图书数据源。
- 书单量超过 1000 条，一次全量返回开始不合理。
- 需求方提出读书也要进周报/月报或单独的年度阅读报表。

## 替代成本参考

阅读记录类产品（Goodreads、豆瓣读书、微信读书）都以「书 + 读完时间 + 短评」为核心，评分与在读状态是后加的社交/统计层；个人自用工具只留最小三件套（书名、读完时间、心得）足够翻看。月末/年末自动汇总阅读清单是常见诉求，本条明确先不做，留给复查条件。
